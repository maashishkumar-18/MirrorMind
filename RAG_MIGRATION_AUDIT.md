## Migration Risk Summary

Priority order — most likely to break silently, cause data loss, or blow the schedule first.

1. **The shared `RetrievedChunk`/`CitationLocationType` contract (`src/common/types.py`) is a single choke point consumed by both retrieval and generation.** A schema change here is a coordinated two-pipeline breaking change, not an isolated edit — the module's own docstring explains it was unified specifically so retrieval and generation never need a conversion step, which means there's no seam to change one side without the other.
   *Mitigation:* land the new session-shaped type(s) alongside the old ones (new name or version flag), port retrieval and generation call sites in the same change, delete the old fields only once both sides compile and pass characterization tests.

2. **Zero automated test coverage anywhere in the repo** (`tests/` is empty; every `__main__` block is a manual, unassertive smoke test hardcoded to one PPTX). Refactoring `RetrievedChunk`, the vector store, and the chunker simultaneously with no regression safety net is how a "successful-looking" migration ships silent behavior changes in BM25 scoring, score fusion, or confidence thresholds.
   *Mitigation:* write characterization tests against current behavior for the KEEP-AS-IS and reusable-shape MODIFY components (BM25, score fusion, confidence scorer, prompt substitution) *before* touching the schema — pin today's behavior first, then change the inputs.

3. **Direct-query structured tables (reminders/todos/meetings/schedules) are a 100% net-new capability** — all three pipeline audits independently confirmed there is no schema, routing logic, or merge-with-semantic-chunks pathway anywhere in the codebase today.
   *Mitigation:* design this schema and its routing boundary (structured-table lookup vs. semantic search vs. both) before rewriting the chunk metadata schema — generation and retrieval will both need to consume its output, so getting the shape right early avoids a second migration.

4. **Retrieval and ingestion both import the concrete Pinecone-backed `VectorStore` directly — no interface boundary exists**, unlike embeddings, which already have a proper `EmbeddingProvider` ABC. Swapping to SQLite means touching call sites in two pipelines simultaneously, and `hybrid_search.py` also instantiates ingestion's `EmbeddingGenerator` directly at query time, so the coupling runs both directions.
   *Mitigation:* introduce a `VectorStoreInterface` ABC in `src/common/` first, wrap Pinecone behind it with zero behavior change, verify nothing broke, *then* swap the implementation for SQLite — de-risks the actual cutover into two independently-verifiable steps.

5. **Two pre-existing, unrelated bugs will get silently blamed on the migration if not caught first**: (a) `vector_store.py`'s hardcoded `DIMENSIONS=3072` doesn't match the embedder's own default model (`gemini-embedding-001` = 768 dims) — the default config already fails dimension validation today; (b) `tools/retrieval_debug_server.py` reads `c.page_start`/`c.page_end`, attributes that don't exist on `RetrievedChunk` — this endpoint throws `AttributeError` right now whenever chunks are non-empty.
   *Mitigation:* fix or explicitly document both before starting, so they aren't mistaken for regressions introduced by the schema change during migration debugging.

6. **`RetrievalOrchestrator`'s fallback-degradation path is dead code that would crash if invoked** — `_fallback_search`/`_fallback_reranker` (orchestrator.py:743-808) import classes that don't exist under those names/paths and construct dataclasses with mismatched kwargs. The system's apparent "graceful degradation on component failure" safety net does not actually work, and nothing short of reading the code (not a test failure) would reveal this.
   *Mitigation:* fix or remove before migration — don't assume today's fallback behavior is real when reasoning about failure modes in the new architecture.

7. **Eval/CI quality gates are wired to exact prompt wording and a 100%-document-only golden set.** `REFUSAL_PATTERNS` regexes the literal phrase "does not cover ... in sufficient detail" out of `context_aware.yaml`'s system prompt; `eval/golden_qa_set.json` is 101 items keyed to one PPTX with `expected_slides`/verbatim `source_quote`. Rewriting prompts for session/memory framing silently breaks the CI eval gate unless both are rewritten together.
   *Mitigation:* treat "new golden set (session/memory questions) + new refusal-detection regex" as a hard prerequisite for shipping new prompt templates, not a follow-up task — otherwise CI will either false-fail on everything or (worse) silently stop measuring refusal rate at all.

8. **Cost/usage accounting is 100% cloud-token-based** (`src/common/pricing.py`, Langfuse cost spans, the dashboard's cost KPI/charts) and has exactly one hardcoded provider (DeepSeek) wired into three separate call sites across two pipelines and one tool. Once local Ollama inference replaces cloud calls, this either silently reports `$0.00` everywhere or crashes on an unhandled provider string, with no signal that the metric itself has become meaningless.
   *Mitigation:* decide up front what "cost" means for local inference (nothing? compute time?) and update `estimate_deepseek_cost`'s call sites and the dashboard's cost panel together — don't let it fail silently.

9. **Chunk token-budget math is already using the wrong tokenizer for the wrong model** — `chunker.py` measures chunk size with `tiktoken.encoding_for_model("text-embedding-3-small")` (an OpenAI tokenizer) even though the embedder's own default is Gemini, and the migration target (`all-MiniLM-L6-v2`) is a sentence-transformers model with an entirely different, non-tiktoken-compatible tokenizer. This isn't a migration-introduced gap — the current numbers (512/75 token bounds) are already measured against the wrong yardstick.
   *Mitigation:* don't port the existing 512/75-token constants as-is; re-derive chunk-size bounds using `all-MiniLM-L6-v2`'s actual tokenizer and max-sequence-length (384 tokens for this model family) from scratch.

10. **LLM call-site provider selection is inconsistent and partly hardcoded below the pluggable-adapter layer.** `LLMClient`/`ProviderRegistry` genuinely supports pluggable providers, but the low-level `simple_generate()` helper — used by ingestion's chunker/metadata_extractor and retrieval's reranker/retrieval_agent (4 call sites across 2 pipelines) — hardcodes `DeepSeekAdapter()` directly, bypassing the registry entirely.
    *Mitigation:* fix provider resolution once, in `src/common/llm_client.py`'s `simple_generate()`, before touching any pipeline-specific call site — otherwise "switching to Ollama" silently leaves 4 call sites still hitting DeepSeek.
